Findings

1. INTEGRATION_ID still mismatches on 9/9 rows — unchanged from run 330171

HRD/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase.json's JDBC_2 query (as checked in) still literally reads CAST(NULL AS VARCHAR2(250)) AS INTEGRATION_ID, and the handoff confirms this column was untouched by the fix and is unchanged at 9/9 in run 330178. My prior classification's evidence stands unmodified: Workflows/HHS_SDE_ORA_GTASActivityBalanceFact.XML line 210 has EXPRESSION="" for out_INTEGRATION_ID inside a mapping flagged ISVALID="YES" at line 96 — an empty output-expression port could not validate, so the export almost certainly dropped the real expression text, while the target's real, already-loaded data (<JE_HEADER_ID>~<JE_LINE_NUM> pattern, confirmed in run 330171's mismatchedRows) proves a real rule exists in production. Nothing in this run changes that conclusion.

Evidence: HRD/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase.json line 27 (JDBC_2 query text, still CAST(NULL ...)); Workflows/HHS_SDE_ORA_GTASActivityBalanceFact.XML lines 96, 210; run 330178 handoff summary ("INTEGRATION_ID = 9/9 (unchanged...)").

2. PROVIDER_RECIPNT_ID/NAME mismatches dropped sharply: 8/9→2/9 and 6/9→2/9, and the matching 7 rows include non-trivial branches

The 7 now-matching rows are not all trivial: they include two 075-prefixed 7-digit codes (0751234→CDC, 0750350→FDA, per the handoff) that require the intra-HHS OPDIV lookup branch to resolve correctly, one plain 4-digit code (0121500→DEPARTMENT OF AGRICULTURE) requiring the other lookup branch, plus the M/O/B/blank-type rows. That is meaningful positive signal that whatever the new formula's non-C/S fallback path does, it now reproduces the target's real values across multiple distinct branches simultaneously for ID and NAME — this was not true in run 330171, where even the fallback-equivalent logic (the old straight PARENT_AWARD_ID passthrough) failed on all but the blank rows.

I cannot fully audit why the fallback path now succeeds, because I do not have the literal SQL text of the deployed JDBC_2 query for run 330178 — only the paraphrase in the handoff (an NVL(HCA.ATTRIBUTE1, <fallback CASE>) structure for type 'C', analogous for 'S'). That paraphrase implies the fallback branch is keyed on something other than the raw synthetic PARENT_AWARD_ID value that failed to resolve in run 330171 (since the same synthetic-looking source rows now produce correct real-world codes) — but I cannot confirm the exact key column from the evidence available to me. See Gaps.

Evidence: handoff summary, row-by-row detail table for CCID 10001–10009 (paraphrased formula fragments); Workflows/HHS_SDE_ORA_GTASActivityBalanceFact.summary.json field_lineage entries for PROVIDER_RECIPNT_ID/PROVIDER_RECIPNT_NAME (confirms the checked-in XML does not contain this richer logic at all — see Finding 4).

3. Two rows still mismatch: CCID=10001 (type 'C', TRADING_PARTNER_ID=1001) and CCID=10002 (type 'S', TRADING_PARTNER_ID=2001) — both resolve to NULL on the expected (B) side

Per the handoff: for type 'C', the formula is NVL(HCA.ATTRIBUTE1, <fallback CASE>) where HCA is a LEFT JOIN apps.HZ_CUST_ACCOUNTS filtered to LENGTH(ATTRIBUTE1)=4, joined ON TRADING_PARTNER_ID = CUST_ACCOUNT_ID. If no HZ_CUST_ACCOUNTS row has CUST_ACCOUNT_ID=1001, HCA.ATTRIBUTE1 is NULL by construction of the outer join. The described fallback CASE is then guarded by a TRADING_PARTNER_ID IS NULL condition — but TRADING_PARTNER_ID is populated (1001) for this row, so that guard also fails, and the whole expression evaluates to NULL. The type 'S' row (CCID=10002, TRADING_PARTNER_ID=2001) fails the same way against apps.AP_SUPPLIERS.VENDOR_ID.

Two candidate root causes are both consistent with the evidence I have, and I cannot distinguish between them without more information than was supplied:

  • Missing reference data: apps.HZ_CUST_ACCOUNTS/apps.AP_SUPPLIERS genuinely lack rows for CUST_ACCOUNT_ID=1001/VENDOR_ID=2001 in this environment, and would resolve correctly against a fuller data set.
  • Fallback-guard design gap in the new formula itself: the fallback CASE's guard condition is TRADING_PARTNER_ID IS NULL, which reads like a condition meant to handle the case where TRADING_PARTNER_ID itself is absent (plausibly written for the non-C/S row types) — not the case where TRADING_PARTNER_ID is present but the join to HZ_CUST_ACCOUNTS/AP_SUPPLIERS simply finds no match. If the intent of wrapping the fallback in NVL(...) was "fall back whenever the primary join misses," the guard should arguably test something else (e.g. re-test on HCA.CUST_ACCOUNT_ID IS NULL), and as written the fallback can never actually fire for a type-'C'/'S' row with a populated TRADING_PARTNER_ID and no matching account — which is exactly what's observed for both remaining rows.

I do not have the literal SQL, nor visibility into the actual contents of apps.HZ_CUST_ACCOUNTS/apps.AP_SUPPLIERS in this environment, so I cannot resolve which of these it is. See Recommended Actions and Gaps.

Evidence: handoff summary, CCID 10001 and 10002 row detail (formula paraphrase, target values '1200'/DEPARTMENT OF ENERGY and '1400'/DEPARTMENT OF JUSTICE vs. NULL on the expected side).

I do not have the literal deployed SQL text (only the paraphrase in the handoff) or visibility into the actual reference-table contents, so I cannot pick between these two.
