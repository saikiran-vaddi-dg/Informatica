Findings

1. All 9 matched-key rows agree exactly, including the computed ROUND(AMOUNT,2) column

The report's Matched Rows section lists all 9 rows present in the target (CCID 10001–10009) with identical CCID, PERIOD_NUM, SET_OF_BOOKS_ID, and AMOUNT values on both sides (e.g. 10002 / 9 / 2021 / 275500.50, 10008 / 9 / 2021 / 8750.25). Column Wise Mismatches reports "No data available," and the Duplicates In JDBC_1/JDBC_2 sections are both empty. This confirms the trivial transformation logic this mapping actually encodes — a straight passthrough of the three key columns plus ROUND(AMOUNT,2) on AMOUNT, per EXP_QUICKDEMO's TRANSFORMFIELD in Workflows/HHS_SDE_ORA_QuickDemoFact.XML line 37 — is not, in itself, wrong wherever it has been applied.

Evidence: Results/..._run330247_report.json → Matched Rows, Column Wise Mismatches; Workflows/HHS_SDE_ORA_QuickDemoFact.XML line 37.

2. Given task context, these 9 "matched" rows are very unlikely to be evidence this mapping has ever actually run

Per the standing context for this analysis, W_GTAS_ACTIVITY_BALANCES_FS is the same physical target table the production HHS_SDE_ORA_GTASActivityBalanceFact workflow loads (verified independently: both XMLs name the identical target, W_GTAS_ACTIVITY_BALANCES_FS), and HHS_SDE_ORA_QuickDemoFact itself appears never to have been executed against real data. The 9 rows this test finds matching are therefore best read as incidental overlap — the production GTAS workflow's own load happens to agree with this mapping's narrower 4-column/3-key projection on those 9 rows, not proof that HHS_SDE_ORA_QuickDemoFact itself produced them.

This reading is reinforced by the test case's own _notes (HRD/HHS_SDE_ORA_QuickDemoFact_TestCase.json): "(CCID, PERIOD_NUM, SET_OF_BOOKS_ID) is used here as the DataCompare key to match the 4-column scope of this mapping's own target field list, but it is NOT the true unique grain of the shared physical target table," and by OKF/workflows/HHS_SDE_ORA_QuickDemoFact/hrd_mapping.md's own caveat that this mapping's name and narrow scope "suggest it is a demo/tutorial artifact rather than a mapping meant to run against that same production target as a real ETL load."

Evidence: Workflows/HHS_SDE_ORA_QuickDemoFact.XML line 13 (target name) vs. shared-target context provided for this task; HRD/HHS_SDE_ORA_QuickDemoFact_TestCase.json _notes[1]; OKF/.../hrd_mapping.md "Known Caveats."

3. The one "only in source" row, CCID=10010, is the same gap already flagged for the production workflow's own test case

The single failing row here — CCID=10010, PERIOD_NUM=9, SET_OF_BOOKS_ID=2021, AMOUNT=500000.00 — is a 10th source row not present in the target at all. This is notable because Results/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase_v2_run330171_analysis.html (Finding 3, run against the same shared source/target pair) independently found exactly one "only in source" row and attributed it to the production workflow's real incremental filter ($$LAST_EXTRACT_DATE in SQ_FV_GTAS_ACTIVITY_BALANCES, XML line 258 of that workflow) having no resolvable value in this environment, so the newest source row has not yet been picked up by any load path — production or otherwise.

HHS_SDE_ORA_QuickDemoFact's own source qualifier has no filter at all (Sql Query and Source Filter both empty, confirmed directly in Workflows/HHS_SDE_ORA_QuickDemoFact.XML lines 25 and 27) — so if this mapping had ever actually run, it would have picked up all 10 source rows unconditionally, including CCID=10010. The fact that CCID=10010 is still missing from the target is additional, independent evidence that this mapping's own execution is what's actually missing here, not a filtering/logic gap in the mapping itself.

Evidence: Results/..._run330247_report.json → Only In JDBC_2 (row 10010 / 9 / 2021 / 500000.00); Workflows/HHS_SDE_ORA_QuickDemoFact.XML lines 25, 27 (no source filter); Results/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase_v2_run330171_analysis.html Finding 3.

Recommended Actions

No action needed — test case is correct

Findings 1 & 3, test-case mechanics. The JDBC_1/JDBC_2 queries, the 4-column mapping, and the 3-column composite key (CCID, PERIOD_NUM, SET_OF_BOOKS_ID) are a faithful, verified translation of HHS_SDE_ORA_QuickDemoFact's actual mapping logic (confirmed line-by-line against Workflows/HHS_SDE_ORA_QuickDemoFact.XML: no source filter, straight passthrough of the 3 key columns, ROUND(AMOUNT,2) on AMOUNT). Do not loosen the onlyInBThreshold (currently 0, per HRD/HHS_SDE_ORA_QuickDemoFact_TestCase.json config) to force a pass — that would silently paper over a real gap rather than fix it.

Environment/data defect — workflow never executed against real data

Finding 2, root cause of the Failed status. This is not a defect in the test case and not a bug in the mapping's (trivial) transformation logic — it is that HHS_SDE_ORA_QuickDemoFact itself has apparently never actually run an ETL load into W_GTAS_ACTIVITY_BALANCES_FS. The 9 "matching" rows this run found are best explained as incidental overlap with the separate production HHS_SDE_ORA_GTASActivityBalanceFact workflow's real loads on the same shared table, not as evidence of this mapping's own execution. What needs to change (outside this test case): either (a) actually execute the HHS_SDE_ORA_QuickDemoFact_PSC session/workflow for real so the target genuinely reflects this mapping's output, after which this DataCompare would be validating something meaningful either way; or (b) if this mapping is confirmed to be a demo/tutorial artifact never intended to load into the shared production target table (as both the test case's own _notes and the OKF caveat already suspect), retarget this test case to whatever table/environment this mapping is actually meant to write to, rather than continuing to compare it against a production table it doesn't own. Which of (a)/(b) applies is a scoping question for the workflow owner/SME, not something to resolve by editing the test case's query logic.

Environment/data defect (source data not yet loaded by any path)

Finding 3, the CCID=10010 gap specifically. Independent of the "never run" issue above, this same source row was already flagged as missing from the target by the production workflow's own test case (run 330171), attributed there to $$LAST_EXTRACT_DATE having no resolvable value in this environment. Recommended action: resolve that shared root cause once (see the recommendation already on record in Results/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase_v2_run330171_analysis.html) rather than treating it as two separate problems — once the newest source row is genuinely loaded by a real run of either workflow, this "only in source" finding should clear on its own without any test-case change.
