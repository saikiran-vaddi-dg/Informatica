2. PROVIDER_RECIPNT_ID mismatches on 8/9 rows, PROVIDER_RECIPNT_NAME on 6/9

What the XML actually says (verified directly, not from the summary alone): the CONNECTOR lines (315, 318, 331, 396) confirm PROVIDER_RECIPNT_ID really is wired as a straight passthrough of FV_GTAS_ACTIVITY_BALANCES.PARENT_AWARD_ID. PROVIDER_RECIPNT_NAME, however, is not empty and not a simple passthrough — line 213 contains a full nested IIF: 7-char id not starting 075 → LKP_PROVD_RECP(SUBSTR(id,2,2)) against FND_FLEX_VALUES_VL (VALUE_CATEGORY='HHS_TP_ELIMINATION_CODE'); id starting 075 (HHS's own Treasury agency prefix) → LKP_INTRA_HHS_ELI(SUBSTR(id,4,4)) against W_GTAS_INTRAHHS_D.OPDIV; else → LKP_PROVD_RECP(id) directly (lines 97–169 for the two lookup definitions).

This test case's JDBC_2 query (HRD/..._TestCase.json) implements that exact branch structure as a SQL CASE/correlated-subquery translation — same three branches, same tables, same substrings. The test case's expected-side logic is a faithful, correct SQL translation of the checked-in XML. This directly contradicts how the prior pass's HRD _notes characterized it ("does NOT match a simple PARENT_AWARD_ID passthrough/lookup" as if the test case's logic were too simplistic) — the logic is not simplistic, and it does match the XML.

So why does it still fail? Tracing the report's actual row values against the XML's own branch structure is revealing:
