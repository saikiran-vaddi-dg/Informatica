Findings

Finding 1 — X_CUSTOM (10/10 mismatched). The target's real X_CUSTOM values are synthetic placeholder text (X_CUSTOM_N, one per demo row), not derivable from any source expression. The workflow XML's own connector (SQ_BCI_PURCH_RQLNS) wires X_CUSTOM from PO_LINE_LOCATIONS_ALL.ENCUMBERED_FLAG, a Y/N flag — nowhere near the target's placeholder strings. This is expected given this is a demo/POC container with independently-seeded synthetic data on the target side, not a defect in the test case's derivation. This is also why X_CUSTOM was dropped from the unique key this run (see HRD _notes) — it was never a stable join discriminator in this container.
Finding 2 — PO_CREATION_METHOD_ID (10/10 mismatched). The target holds plain numeric strings ("1".."10"); the source-derived value here is the raw DOCUMENT_CREATION_METHOD text carried straight through per this SDE-layer mapping's own logic. The numeric-code lookup (WID resolution against W_XACT_TYPE_D) lives in a later SIL-layer mapping — confirmed by the pre-existing HHS_SIL_PurchaseRequisitionLinesFact_TestCase dataflow already present in this container's WorkingSession folder, which performs that lookup. This SDE test case only validates the raw passthrough, which it does correctly; the mismatch is a layering/expectation artifact of comparing an SDE-stage value to a SIL-stage-shaped target, not a bug in this mapping.
Finding 3 — LINE_AMT / CANCELLED_LINE_AMT / CANCELLED_LINE_QTY / REQUESTED_QTY / UNIT_PRICE (10/10 each) and PO_APPROVED_ON_DT / DELETE_FLG (5/10 each). The target's numeric/date/flag values follow simple synthetic row-number patterns (e.g. UNIT_PRICE values like "N.686...") that are uncorrelated with the computed OLTP-side values, because target and source in this demo container were seeded independently rather than one being generated from the other. This is expected for a POC/demo dataset and mirrors the same conclusion reached in Results/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase_v2_run330178_analysis.html for its own container. It is not evidence of a wrong derivation formula — the MATCHING_BASIS, release-vs-header, and APPROVED_FLAG branches were all confirmed schema/column-existence-correct against the live tables.
Finding 4 — key integrity is clean. 0 only-in-A, 0 only-in-B, 0 duplicates on either side: INTEGRATION_ID alone (TO_CHAR(REQUISITION_LINE_ID)) is a valid, fully-discriminating join key across all 10 rows in both datasets, confirming the composite-key simplification made this run (dropping X_CUSTOM) was correct.
