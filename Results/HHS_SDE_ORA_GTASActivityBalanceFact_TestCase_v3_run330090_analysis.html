Build-time discovery: source table is not partitioned in this environment

The first create_dataflow attempt failed outright with ORA-14501: object is not partitioned — the test case's JDBC_2 query used Oracle PARTITION(P2/P23/P1/P43) hints to read each ledger's physical partition, mirroring how the four Informatica sessions (_FDA/_PSC/_CDC/_IHS) read production. Sample data confirmed the DevContainer's FV_GTAS_ACTIVITY_BALANCES is a flat, unpartitioned 10-row stub table. The PARTITION(...) hints were removed from HRD/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase.json so the dataflow could build and run; this is an environment-fidelity fix, not a change to the intended per-ledger logic, and is documented in the test case's own inline SQL comments.

All four $[GTAS_FISCAL_YR_<LEDGER>_EXT] dataflow parameters were built as documented placeholders defaulting to 0. Every WHERE clause is PERIOD_YEAR IN (0), and no row in the stub source table has PERIOD_YEAR = 0 (actual values are 2024 and 2026), so all four CTEs returned zero rows and the union (JDBC_2) is empty. This run validated the create/run/DataCompare pipeline mechanics end-to-end, but — as already flagged as a known caveat before this build — it could not validate any actual GTAS business logic (provider/recipient lookups, per-ledger correctness, the CCID 10010 gap) because there was nothing in dataset B to compare against.
