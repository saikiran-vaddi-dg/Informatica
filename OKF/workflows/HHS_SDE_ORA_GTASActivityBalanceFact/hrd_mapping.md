## Known Caveats

- **Run 330171 Failed against 0-tolerance DataCompare thresholds** — this is a real reconciliation failure, not a technical/setup error. Full breakdown in the analysis report above.
- **`INTEGRATION_ID` remains a genuine, unresolved XML export gap (confirmed, both runs)** — the currently committed workflow XML's empty `EXPRESSION` attribute for `out_INTEGRATION_ID` (despite `ISVALID="YES"`) does not match live target data: the real target holds values shaped `<JE_HEADER_ID>~<JE_LINE_NUM>` (e.g. `5001~1`), not `NULL`. All 9 matched rows mismatched on this column in both run 330171 and run 330178 — swapping the `PROVIDER_RECIPNT_ID`/`NAME` formula had no effect on it, as expected, since it's a separate expression. This is outside this pipeline's authority to fix without a real Informatica re-export of the mapping; recommend re-exporting/reconciling the production mapping for this port. See analysis reports for evidence.
- **`PROVIDER_RECIPNT_ID` / `PROVIDER_RECIPNT_NAME`: improved but not fully resolved, remaining 2 mismatches accepted as environment/data defect (user-confirmed)** — run 330171 (XML's `PARENT_AWARD_ID`-passthrough/`LKP_PROVD_RECP`/`LKP_INTRA_HHS_ELI` logic) mismatched 8/9 (`PROVIDER_RECIPNT_ID`) and 6/9 (`PROVIDER_RECIPNT_NAME`) rows against live target values. Run 330178, using a richer `TRADING_PARTNER_TYPE`-keyed formula with `LEFT JOIN`s to `apps.HZ_CUST_ACCOUNTS`/`apps.AP_SUPPLIERS`, reduced this to 2/2 mismatches, both on CCID 10001 and 10002. The user has explicitly reviewed and accepted these 2 remaining mismatches as an **environment/data defect** — missing/incomplete reference rows in `apps.HZ_CUST_ACCOUNTS` / `apps.AP_SUPPLIERS` for `TRADING_PARTNER_ID` 1001/2001 — and directed that no further investigation be done; this is documented as accepted, not fixed. Note: analysis-agent separately raised a competing theory that a wrong NULL-guard in the fallback `CASE` expression (rather than missing reference data) could explain these two rows; that theory was **not ruled out**, but the user chose the missing-data classification and moved on — a re-reader who later wants certainty should re-examine both branches before treating this as fully closed.
- **The improved `TRADING_PARTNER_TYPE` formula tested in run 330178 is NOT yet adopted anywhere in checked-in files.** It exists only as an ad hoc query edit made directly against the live dataflow for this experiment. `HRD/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase.json`'s JDBC_2 query still contains the original `PARENT_AWARD_ID`-passthrough logic (run 330171's formula), and the checked-in `Workflows/HHS_SDE_ORA_GTASActivityBalanceFact.XML` has zero representation of the `TRADING_PARTNER_TYPE`/`HZ_CUST_ACCOUNTS`/`AP_SUPPLIERS` logic at all. Its provenance — which live dataflow/mapping actually contains this exact SQL in production — is unconfirmed. **Do not adopt this formula into the HRD test case or the XML until an SME confirms it against the real production mapping**, and until `dataops_mcp` access is restored so the live dataflow definition can be re-verified. This is a follow-up item, not a completed fix.
- **Run 330178's raw DataCompare report was never archived** — no `run330178_report.json` exists on disk. The run happened, and its analysis (`Results/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase_v2_run330178_analysis.html`) was written from data available at the time, but `dataops_mcp` was unreachable when this run was being recorded in this session, so `download_data_compare_report` could not be (re-)called to persist the raw JSON. Re-download it once platform access is restored, for full auditability alongside the 330171 report.
- **1 only-in-source row (CCID=10010, unchanged across both runs)** — plausibly explained by this run being a full-table comparison (the `:LAST_EXTRACT_DATE` bind was removed because it isn't valid on this platform and no real value was known) against a target that was actually last loaded under the real incremental filter; not treated as a defect.
- **Placeholder/unresolved values still present by design**: `DATASOURCE_NUM_ID` is `ignoreColumn: true` and always `NULL` in this test case (driven by unresolved `$$DATASOURCE_NUM_ID` at runtime), and JDBC 2 now runs as a full extract with no incremental filter — see `HRD/HHS_SDE_ORA_GTASActivityBalanceFact_TestCase.json`'s `_notes` for detail.
- **Status is not Validated.** Run 330171 Failed outright; run 330178 improved materially but is recorded as "Failed (improved, pending SME confirmation of formula provenance)" rather than Passed/Validated, because (a) `INTEGRATION_ID` is still unresolved, (b) the formula that produced the improvement is not yet adopted in any checked-in file, and (c) its `Fingerprint` cannot be verified this session (`dataops_mcp` unreachable). Do not schedule this dataflow in the DataGaps native UI as a trusted check until the formula-adoption decision is made, `INTEGRATION_ID` is reconciled, and a clean re-run confirms a matching `Fingerprint`.
