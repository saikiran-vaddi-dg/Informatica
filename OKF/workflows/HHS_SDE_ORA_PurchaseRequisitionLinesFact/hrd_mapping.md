## Known Caveats

- **STD_COST_AMT/UNIT_STD_COST not covered by the test case.** The currency-converted standard cost chain (`MPLT_CURCY_CONVERSION_RATES_All` -> `LOC_TO_DOC` expression -> standard-cost lookup against `W_STANDARD_COST_G`) was not fully traced this session and is explicitly flagged out-of-scope in the test case's `_notes` — add as a follow-up once the mapplet internals are traced.
- **`$$LAST_EXTRACT_DATE`/`$$INITIAL_EXTRACT_DATE` incremental filter not tested.** The Source Qualifier's incremental/CDC branching logic is a run-to-run extraction concern, not testable via a single-snapshot DataCompare; the test case's JDBC_2 query is a full extract.
- **`X_CUSTOM` removed from the unique key this run (run 330248).** The target's real `X_CUSTOM` values are synthetic placeholder text (`X_CUSTOM_N`) unrelated to any derivable source expression (the workflow XML wires `X_CUSTOM` from `PO_LINE_LOCATIONS_ALL.ENCUMBERED_FLAG`, a `Y`/`N` flag). `DATASOURCE_NUM_ID` remains `ignoreColumn: true` for the same reason as before (static mapping parameter). The composite key that actually differentiates rows is `INTEGRATION_ID` alone (`TO_CHAR(REQUISITION_LINE_ID)`) — confirmed via run 330248's clean join (0 only-in-A/B, 0 duplicates on either side).
- **Run 330248 Failed against 0-tolerance thresholds: 10/10 rows had at least one column mismatch, 0 orphaned/duplicate rows (perfect key match on `INTEGRATION_ID`).** Root cause per analysis-agent: this is a demo/POC container with independently-seeded synthetic data on both the target (`W_PURCH_RQSTN_LINE_FS`) and source (Oracle EBS OLTP) sides — not a defect in the SQL/derivation logic. See `Results/HHS_SDE_ORA_PurchaseRequisitionLinesFact_TestCase_run330248_analysis.html` for the full column-by-column breakdown (notably `PO_CREATION_METHOD_ID`'s mismatch reflects an SDE-vs-SIL layering artifact, not a wrong formula — the numeric-code lookup happens in the separate `HHS_SIL_PurchaseRequisitionLinesFact_TestCase` dataflow already present in this container).
- **No code fix applied.** Per this repo's classify-and-confirm convention, an environment/data-defect classification does not get remediated by editing the test case or the mapping — schema-qualification and the `DELETE_FLG` correction were already applied and validated as part of reaching this run; the remaining mismatches are accepted as demo-data noise, not a scope requiring further fixes.
- **Status is not Validated.** This row is recorded as Failed (with root cause explained above), not Passed — do not schedule this dataflow in the DataGaps native UI as a trusted check based on this run.
- **Run 330259 is a re-verification pass, not a new investigation.** A harmless, unwired Expression transformation (`EXP_TEST_VERIFY_TRIM_DESCRIPTION`, not connected to any other transformation or target field) was added to `Workflows/HHS_SDE_ORA_PurchaseRequisitionLinesFact.XML` solely to bump its content hash and exercise this pipeline's drift-detection/reprocessing path end-to-end for a real second-pass time/token comparison. review-agent confirmed the existing `HRD/HHS_SDE_ORA_PurchaseRequisitionLinesFact_TestCase.json` test case needed no changes. Run 330259 against the same deployed dataflow reproduced run 330248's outcome exactly (same counts, same column-wise mismatch counts), confirming the dangling transformation has no effect on results, as expected.
